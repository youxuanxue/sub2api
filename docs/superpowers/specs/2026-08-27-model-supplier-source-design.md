# TokenKey 模型供应源管理与自动接入设计

## 1. 目标

运营只需告诉 TokenKey：从哪个供应通道、以什么采购比例、采购哪些模型。系统负责把这份
运营事实投影成隔离账号、明确模型映射和账号调度优先级，并经真实协议/模型探测后热更新。

体验目标：

```text
填写供应事实与凭证 → 自动验证 → 看结果并确认启用
```

运营不管理 `account_id`、`platform`、`channel_type`、`model_mapping`、`priority`、
`group_id` 或 runtime setting。它们都是系统生成的执行投影。

## 2. 非目标与隔离边界

本设计不：

- 读取或写入 TokenKey `rate_multiplier`；
- 读取或写入模型售价、pricing registry、渠道定价或计费规则；
- 根据采购比例推导用户售价、利润或倍率；
- 把采购比例暴露到用户 API；
- 自动适配未知供应商私有协议；
- 在没有凭证时凭空完成账号接入；
- 创建账号后未经验证直接加入生产调度。

供应源采购比例是内部采购与调度元数据，唯一运行作用是派生供应账号之间的相对优先级。
健康、冷却、限流、容量和可调度性仍由现有调度安全规则拥有，并可压过采购优先级。

## 3. 乔布斯式复杂度复审

### 3.1 只给运营一个对象

唯一管理对象是“供应源”：一个凭证、一个上游地址、一个合同模型组、一个统一采购比例。

不单独建设供应商、合同、模型库、账号绑定或发布配置页面。供应商名称和通道名称是供应源
字段；模型是供应源中的结构化列表；账号是内部投影。

### 3.2 只让运营做两个判断

1. 输入真实采购信息和凭证。
2. 查看真实探测结果并决定是否启用。

系统自动完成账号匹配/创建、协议探测、模型探测、映射生成、优先级派生和缓存刷新。

### 3.3 不做双向编辑

供应源是受管字段的唯一 owner。绑定账号中的模型映射和采购派生 priority 是只读投影。
管理员账号页面仍可查看技术细节，但不能绕过供应源修改这些受管字段；紧急解除托管必须是
显式、审计化动作。

## 4. 供应源数据契约

### 4.1 运营输入

```text
id                     系统 ID
supplier_name          供应商，例如“佳杰”
channel_name           合同/模型组，例如“stbl-5”
endpoint               上游基地址
purchase_ratio         相对模型官方价格的采购比例，0 < ratio <= 1
models[]               明确模型清单
capacity               TPM/RPM/并发，可选
expandability          expandable / fixed / unknown
credential_ref         凭证保管引用，不保存可回显明文
state                  draft / verifying / ready / enabled
revision               乐观锁修订号
```

`models[]` 每项只有：

```text
client_model_id        TokenKey 对外模型 ID
upstream_model_id      上游实际型号；初始可空，探测后必须明确
capability             chat / responses / messages / embedding / image / video
probe_result           系统生成，不由运营编辑
```

### 4.2 必须拆分供应源的条件

以下任何一项不同就拆成两个供应源：

- 凭证不同；
- endpoint 不同；
- 合同模型组不同；
- 采购比例不同。

因此佳杰的 `stbl-5 / 5折`、`zq-gd / 4.3折`、`dxbl / 4.5折` 是三个供应源，
即使域名相同。这样每个投影账号只有一个采购优先级，避免引入模型级调度新系统。

### 4.3 输入硬校验

- `purchase_ratio` 必须是数值；`43折`、`55折` 等自由文本拒绝保存，不能自动猜小数点。
- 禁止“全系列”或普通 `*`；必须展开明确模型。
- `client_model_id` 在同一供应源内唯一。
- enabled 前每个模型必须有明确的 `upstream_model_id` 和通过的能力探测。
- endpoint 规范化后用于发现已有账号，但不得仅凭同域名自动绑定；还要核对凭证引用和通道。

## 5. 现有账号与新渠道统一流程

### 5.1 查找已有账号

保存供应源后，系统按规范化 endpoint、非敏感凭证指纹和通道类型查找账号：

- 唯一匹配：生成绑定预览；
- 无匹配：进入隔离建号；
- 多个匹配：停止并让管理员选择，系统不猜。

已有账号若正在承接生产流量，验证过程使用现有保留探测资源，不改变其正式分组或调度状态。

### 5.2 隔离建号

无匹配账号时复用 `ops/accounts/import-accounts.py` / Admin create-account 能力，创建候选账号：

```text
status = inactive
schedulable = false
不绑定正式业务组
仅供受控探测使用
```

候选账号创建与供应源绑定必须幂等：相同供应源修订重试不得生成重复账号。凭证由现有 secret
路径注入，不写日志、不写供应源普通字段、不回显。

### 5.3 平台和 channel type 的归属

运营不选择 TokenKey platform/channel type。接入编排器根据探测结果选择已支持 transport：

- OpenAI Chat/Responses/Embedding；
- Anthropic Messages；
- 已有 NewAPI channel；
- 已有标准图片/视频端点。

若存在多个同等有效 transport，系统给出推荐和证据，但启用前需管理员确认；不能用请求顺序
静默决定。

## 6. 协议与模型探测

### 6.1 有界协议矩阵

隔离账号只执行已知、低成本探测：

```text
GET  /v1/models
POST /v1/chat/completions
POST /v1/responses
POST /v1/messages
POST /v1/embeddings       仅 embedding 候选
标准图片端点              仅 image 候选
标准视频端点              仅 video 候选
```

复用现有 `AccountTestService`、协议 capability probe 和
`probe_account_model.sh` 的真实账号归属校验，不另建第二套探测引擎。

探测结果必须区分：endpoint 不存在、鉴权失败、模型不存在、请求不兼容、上游成功、
TokenKey 路径成功但命中错误账号。只有真实成功且账号归属匹配才算通过。

### 6.2 模型清单三层事实

```text
上游 /models 返回 = 候选集合
运营采购清单      = 期望集合
真实模型探测通过  = 可启用集合
```

最终账号 `model_mapping` 只由“期望集合中探测通过的明确映射”完整生成。`/models` 返回但
不在采购范围的型号不自动加入；采购型号探测失败也不静默加入。

### 6.3 私有协议边界

未知异步协议不做启发式上线。系统保留候选账号并输出：

```text
鉴权是否成功
命中的已知协议
失败端点及脱敏原因
结论：需要供应商适配器
```

适配器是独立研发任务；完成后同类供应源才能复用自动接入。FMGo 是此边界的验收案例。

## 7. 优先级派生

### 7.1 语义

`purchase_ratio=0.50` 表示采购成本为模型官方价格的 50%。对能够服务同一
`client_model_id` 的 enabled 供应源，ratio 越小，供应顺序越靠前。

### 7.2 账号级相对档位

系统不把比例直接写成 priority，也不引用 TokenKey 售价。对同一可比供应池按采购比例稳定排序：

```text
最低 ratio       → priority 10
第二低 ratio     → priority 20
第三低 ratio     → priority 30
……
```

相同 ratio 使用相同采购档位，再由现有健康、容量和同优先级调度规则选择。稳定 tie-breaker 只用于
确定性输出，不改变相同采购比例的语义。

由于当前 TokenKey priority 是账号级字段，一个供应源中的所有模型必须共享采购比例。若同一凭证
下不同模型价格不同，拆成独立供应源和独立投影账号，不扩建模型级 priority。

### 7.3 变更影响

新增、暂停或修改一个供应源的 ratio 时，只重算与其模型集合相交的受管账号；不批量重写
无关平台或 OAuth 动态优先级账号。非供应源托管账号不纳入采购排序。

## 8. 状态与操作

主状态只保留四个：

```text
draft → verifying → ready → enabled
```

- 验证失败回到 `draft`，在模型行显示原因，不新增一串失败状态。
- enabled 供应源可以“暂停”；暂停后立即退出调度，但保留配置与审计记录。
- 删除采用归档，不直接删除账号与历史。

运营动作只有：保存草稿、验证、启用/暂停。验证可以由保存后自动触发；凭证缺失时停在草稿。

## 9. 启用事务与热更新

点击“启用”前显示单一预览：

```text
将绑定/创建哪个账号
哪些模型会启用或移除
协议探测结论
采购比例与同模型供应顺序
账号 priority 的前后值
正式分组变化
```

确认后执行一次受控激活：

1. 锁定供应源 revision，确认凭证和探测证据仍有效；
2. 完整替换账号 `model_mapping`，禁止不透明增量合并；
3. 写入派生 priority；
4. 绑定正式组；
5. 设置 active、schedulable；
6. 复用现有 account change/outbox 机制刷新调度快照；
7. 回读账号并严格比对期望；
8. 任一步失败则不让候选账号进入生产池。

数据库内字段尽可能同事务写入；外部缓存刷新失败时账号保持不可调度并进入可重试的收尾动作，
不能出现“部分配置已经承接生产流量”的状态。

已有 production 账号的模型移除、解绑、暂停以及 ratio 导致的优先级重排，都必须进入相同预览与
确认门禁。普通新增且不删除能力仍需启用确认，因为它会产生真实上游流量。

## 10. 失败处理与审计

每次验证和启用记录：供应源 revision、操作人、时间、候选/绑定账号、协议结论、逐模型结果、
期望与实际 diff。记录不得含 API key、OAuth token、cookie 或完整响应正文。

重试规则：

- 网络超时可重试，不改变供应源意图；
- 401/403 停止并要求更新凭证；
- 未知协议停止并要求适配器；
- 多账号匹配停止并要求选择；
- 模型部分失败时只展示结果，不允许整源 enabled；运营可删除失败型号后重新验证。

## 11. 首批验收案例

### 11.1 佳杰 / VSTECS：标准协议自动接入

以 `stbl-5` 为一个供应源：输入 endpoint、凭证、0.50 采购比例和明确模型。系统应创建
不可调度候选账号，识别标准 transport，逐模型探测，生成完整映射和启用预览；确认后才进入
生产组。`zq-gd` 等不同采购比例模型组必须生成独立供应源/账号。

### 11.2 FMGo：协议边界

输入 Seedance 2.0 480p/720p 供应源。若标准视频探测通过，则走自动接入；若识别为私有异步
任务协议，候选账号保持不可调度，页面明确显示需要供应商适配器，无任何猜测式上线。

### 11.3 已有百度账号：绑定而非重复创建

以规范化 endpoint 和非敏感凭证指纹唯一匹配账号 90，系统应生成绑定预览而不是新建账号；
验证不得临时把当前不可调度账号加入业务流量。

## 12. 验收标准

- 运营完成新渠道接入无需理解或填写 TokenKey 技术字段。
- 无匹配账号时可幂等创建不可调度候选账号并自动绑定。
- 标准协议、模型清单和逐模型能力均使用真实请求验证。
- 未知协议明确停止，绝不进入生产池。
- 只有期望且探测通过的明确模型进入完整 `model_mapping`。
- 同模型供应源严格按采购比例形成相对账号 priority；相同比例同档。
- 采购比例不读写倍率、定价、计费或用户接口。
- 启用失败时不存在部分上线账号。
- 受管账号不能从账号编辑页产生与供应源相冲突的模型映射或 priority。
- 所有变更可审计，所有敏感凭证不进入日志与普通业务字段。

## 13. 实现范围控制

第一版只实现：单供应源编辑、已有账号唯一匹配、标准 API Key 候选账号创建、标准协议/模型探测、
完整 mapping、账号级优先级派生、确认激活和审计。

第一版不实现：合同附件、审批流编排、利润分析、采购账单、供应商门户、任意私有协议低代码配置、
模型级 priority、自动修改 TokenKey 售价或倍率。
