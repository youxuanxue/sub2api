# TokenKey 模型供应源管理与自动接入设计

## 1. 目标

运营只需告诉 TokenKey：从哪个供应通道、以什么采购比例、采购哪些模型。系统负责把这份
运营事实投影成隔离账号、明确模型映射和账号调度优先级，并经真实协议/模型探测后热更新。

体验目标：

```text
填写供应事实与凭证 → 自动验证 → 看结果并确认启用
```

运营不管理 `account_id`、`platform`、`channel_type`、`model_mapping`、`priority`、
`group_id` 或 runtime setting。它们都是系统生成的执行投影。

## 2. 非目标与隔离边界

本设计不：

- 读取或写入 TokenKey `rate_multiplier`；
- 读取或写入模型售价、pricing registry、渠道定价或计费规则；
- 根据采购比例推导用户售价、利润或倍率；
- 把采购比例暴露到用户 API；
- 自动适配未知供应商私有协议；
- 在没有凭证时凭空完成账号接入；
- 创建账号后未经验证直接加入生产调度。

供应源采购比例是内部采购与调度元数据，唯一运行作用是派生同一模型的供应顺序。顺序固定为：

1. TokenKey 原生 OAuth 账号；
2. 声明采购比例的供应商账号，采购比例越低越优先；
3. 未声明采购比例但经探测支持该模型的供应商账号，作为最低优先级兜底。

健康、冷却、限流和可调度性仍由现有调度安全规则拥有，并可压过采购顺序。

## 3. 乔布斯式复杂度复审

### 3.1 只给运营一个对象

唯一管理对象是“供应源”：一个供应商通道、一个上游地址和一份凭证。不同模型可以有不同
采购比例；系统按模型供给项自动投影执行账号，运营不管理这些账号。

不单独建设供应商、合同、模型库、账号绑定或发布配置页面。供应商名称和通道名称是供应源
字段；模型是供应源中的结构化列表；账号是内部投影。

### 3.2 只让运营做两个判断

1. 输入真实采购信息和凭证。
2. 查看真实探测结果并决定是否启用。

系统自动完成账号匹配/创建、协议探测、模型探测、映射生成、优先级派生和缓存刷新。

### 3.3 不做双向编辑

供应源是受管字段的唯一 owner。绑定账号中的模型映射和采购派生 priority 是只读投影。
管理员账号页面仍可查看技术细节，但不能绕过供应源修改这些受管字段；紧急解除托管必须是
显式、审计化动作。

## 4. 供应源数据契约

### 4.1 运营可编辑字段

```text
supplier_name          供应商，例如“佳杰”
channel_name           合同/模型组，例如“stbl-5”
endpoint               上游基地址
models[]               明确模型与各自采购比例
credential             API Key 等接入凭证；保存后不回显
notes                  开放备注，可空，不参与任何运行判断
```

`models[]` 的运营输入每项只有：

```text
client_model_id        TokenKey 对外模型 ID
upstream_model_id      上游实际型号；初始可空，探测后必须明确
purchase_ratio         该模型相对官方价格的采购比例；可空，0 < ratio <= 1
```

系统内部另存 ID、凭证引用、状态、revision、能力与探测结果；它们不是运营字段。除 `notes` 外
不增加容量、扩容能力、合同附件等非核心输入。未来只有当一个字段会改变接入或调度决策，且不能
从线上事实派生时，才考虑进入结构化契约。

### 4.2 供应源边界与执行投影

以下任何一项不同就拆成两个供应源：

- 凭证不同；
- endpoint 不同；
- 供应商通道不同。

同一供应源允许不同模型使用不同采购比例。由于 TokenKey 当前 priority 是账号级字段，系统按
采购档位把一个运营供应源投影成一个或多个执行账号：采购比例相同的模型可以共用账号，不同比例
的模型进入不同投影账号；这些账号复用同一内部凭证引用，但各自只有对应模型的完整
`model_mapping` 和一个账号级 priority。这样既保持运营对象单一，也不引入模型级调度新系统。

佳杰 `stbl-5` 是一个供应源；如果其中 GLM 和 DeepSeek 采购比例不同，界面仍是一张供应源卡片，
系统内部生成两个执行账号。佳杰 `zq-gd` 是另一个供应商通道，因此是另一个供应源。

### 4.3 输入硬校验

- 非空 `purchase_ratio` 必须是数值；`43折`、`55折` 等自由文本拒绝保存，不能自动猜小数点。
- `purchase_ratio` 可以为空；为空不阻止探测和启用，但该模型供给只能进入最低优先级兜底档。
- 禁止“全系列”或普通 `*`；必须展开明确模型。
- `client_model_id` 在同一供应源内唯一。
- enabled 前每个模型必须有明确的 `upstream_model_id` 和通过的能力探测。
- endpoint 规范化后用于发现已有账号，但不得仅凭同域名自动绑定；还要核对凭证引用和通道。

### 4.4 凭证：默认 API Key，不默认保管后台密码

默认要求供应商提供最小权限 API Key，而不是后台账号密码。后台密码权限过大，常受 MFA、验证码、
登录风控和页面变化影响；把浏览器登录自动化作为通用接入路径既不确定，也扩大凭证泄露和误操作
半径。

仅当某供应商已有经过审计的专用连接器时，才允许“输入后台账号 → 自动创建 API Key/模型组”：

1. 密码只进入一次性 secret session，不写供应源、不回显、不进日志；
2. 连接器登录后创建最小权限、可撤销的专用 API Key；
3. TokenKey 只持久化生成的 API Key 引用；
4. 创建结果与权限范围必须展示并确认；
5. MFA、验证码或页面漂移时停止并转人工，不绕过安全控制。

这是一种供应商专用的可选“代建 Key”能力，不是供应源核心字段，也不是第一版通用能力。

## 5. 现有账号与新渠道统一流程

### 5.1 查找已有账号

保存供应源后，系统按规范化 endpoint、非敏感凭证指纹和供应商通道查找受管账号：

- 唯一匹配：生成绑定预览；
- 无匹配：进入隔离建号；
- 多个匹配：停止并让管理员选择，系统不猜。

已有账号若正在承接生产流量，验证过程使用现有保留探测资源，不改变其正式分组或调度状态。

### 5.2 隔离建号

无匹配账号时复用 `ops/accounts/import-accounts.py` / Admin create-account 能力，创建候选账号：

```text
status = inactive
schedulable = false
不绑定正式业务组
仅供受控探测使用
```

候选账号创建与供应源绑定必须幂等：相同供应源修订重试不得生成重复账号。凭证由现有 secret
路径注入，不写日志、不写供应源普通字段、不回显。

### 5.3 平台和 channel type 的归属

运营不选择 TokenKey platform/channel type。接入编排器根据探测结果选择已支持 transport：

- OpenAI Chat/Responses/Embedding；
- Anthropic Messages；
- 已有 NewAPI channel；
- 已有标准图片/视频端点。

若存在多个同等有效 transport，系统给出推荐和证据，但启用前需管理员确认；不能用请求顺序
静默决定。

## 6. 协议与模型探测

### 6.1 有界协议矩阵

隔离账号只执行已知、低成本探测：

```text
GET  /v1/models
POST /v1/chat/completions
POST /v1/responses
POST /v1/messages
POST /v1/embeddings       仅 embedding 候选
标准图片端点              仅 image 候选
标准视频端点              仅 video 候选
```

复用现有 `AccountTestService`、协议 capability probe 和
`probe_account_model.sh` 的真实账号归属校验，不另建第二套探测引擎。

探测结果必须区分：endpoint 不存在、鉴权失败、模型不存在、请求不兼容、上游成功、
TokenKey 路径成功但命中错误账号。只有真实成功且账号归属匹配才算通过。

### 6.2 模型清单三层事实

```text
上游 /models 返回 = 候选集合
运营采购清单      = 期望集合
真实模型探测通过  = 可启用集合
```

最终执行账号 `model_mapping` 只由“期望集合中探测通过、且属于同一采购档位的明确映射”完整
生成。`/models` 返回但不在采购范围的型号不自动加入；采购型号探测失败也不静默加入。

### 6.3 私有协议边界

未知异步协议不做启发式上线。系统保留候选账号并输出：

```text
鉴权是否成功
命中的已知协议
失败端点及脱敏原因
结论：需要供应商适配器
```

适配器是独立研发任务；完成后同类供应源才能复用自动接入。FMGo 是此边界的验收案例。

## 7. 优先级派生

### 7.1 语义

`purchase_ratio=0.50` 表示采购成本为模型官方价格的 50%。排序单位是同一个
`client_model_id`，而不是整个供应商或供应源。

同一模型的业务顺序是：

```text
TokenKey 原生 OAuth
→ 有采购比例的供应商（ratio 从小到大）
→ 无采购比例的供应商兜底
```

“TokenKey 原生 OAuth”只指 TokenKey 直接运营的官方 OAuth 容量或其受信 edge relay，不包括
供应商把 OAuth 包装成的第三方转售渠道。OAuth 是否原生必须由账号来源元数据明确标识，不能根据
`type=oauth` 或账号名称猜测。

### 7.2 账号级相对档位

TokenKey 现有调度语义是 **priority 数值越小，越先被调度**；本设计完全沿用，不引入反向含义。
系统不把采购比例直接当 priority，也不引用 TokenKey 售价。

原生 OAuth 是先于 priority 的调度层，不强行改写其账号 priority。供应商执行账号在自己的层内
生成从 1 开始的稠密 priority：

```text
调度层 1：原生 OAuth   → 沿用现有动态 priority，小值优先
调度层 2：供应商账号
  最低非空 ratio       → priority 1
  第二低非空 ratio     → priority 2
  第三低非空 ratio     → priority 3
……
  ratio 为空的兜底     → 最后一个已报价档位 + 1
```

相同 ratio 使用相同 priority；所有未报价兜底使用同一个最低档。之后由现有健康、冷却和同优先级
调度规则选择。供应商档位从 1 连续递增，直观对齐 TokenKey 小值优先语义，不使用 10/20/30 的
额外刻度。原生 OAuth 与供应商账号不在同一个 priority 数轴竞争，避免供应源编排器覆盖 OAuth
窗口/容量机制动态维护的值。

由于 priority 是账号级字段，同一个执行账号中的模型必须属于同一采购档位。同一运营供应源的
不同模型比例不同时，系统自动拆成多个执行账号；运营仍只管理一个供应源。不扩建模型级 priority。

一个执行账号同时服务多个模型时，其 priority 必须对这些模型都正确。若模型在全局供应池中的相对
档位不同，系统继续拆分执行账号，不能用其中一个模型的档位代表其他模型。

### 7.3 变更影响

新增、暂停或修改一个模型的 ratio 时，只重算与该模型相交的受管执行账号。原生 OAuth 固定占据
第一业务档，但若某类 OAuth 已由现有窗口/容量运维动态管理 priority，供应源编排器不覆盖它；
调度侧应先按“原生 OAuth”来源层选择，再在该层内沿用现有动态 priority。

供应商执行账号使用本设计派生的 priority。无采购比例但支持其他模型的供应商账号只在对应模型
没有更高层可用账号时作为兜底，不影响它有明确 ratio 的其他模型；必要时通过执行账号拆分隔离。

## 8. 状态与操作

主状态只保留四个：

```text
draft → verifying → ready → enabled
```

- 验证失败回到 `draft`，在模型行显示原因，不新增一串失败状态。
- enabled 供应源可以“暂停”；暂停后立即退出调度，但保留配置与审计记录。
- 删除采用归档，不直接删除账号与历史。

运营动作只有：保存草稿、验证、启用/暂停。验证可以由保存后自动触发；凭证缺失时停在草稿。

## 9. 启用事务与热更新

点击“启用”前显示单一预览：

```text
将绑定/创建哪个账号
哪些模型会启用或移除
协议探测结论
逐模型采购比例与供应顺序（原生 OAuth / 已报价 / 未报价兜底）
账号 priority 的前后值
正式分组变化
```

确认后执行一次受控激活：

1. 锁定供应源 revision，确认凭证和探测证据仍有效；
2. 按逐模型采购档位生成或复用执行账号，完整替换各账号 `model_mapping`；
3. 写入与 TokenKey 小值优先语义一致的派生 priority；
4. 绑定正式组；
5. 设置 active、schedulable；
6. 复用现有 account change/outbox 机制刷新调度快照；
7. 回读账号并严格比对期望；
8. 任一步失败则不让候选账号进入生产池。

数据库内字段尽可能同事务写入；外部缓存刷新失败时账号保持不可调度并进入可重试的收尾动作，
不能出现“部分配置已经承接生产流量”的状态。

已有 production 账号的模型移除、解绑、暂停以及 ratio 导致的账号拆分/优先级重排，都必须进入相同预览与
确认门禁。普通新增且不删除能力仍需启用确认，因为它会产生真实上游流量。

## 10. 失败处理与审计

每次验证和启用记录：供应源 revision、操作人、时间、候选/绑定账号、协议结论、逐模型结果、
期望与实际 diff。记录不得含 API key、OAuth token、cookie 或完整响应正文。

重试规则：

- 网络超时可重试，不改变供应源意图；
- 401/403 停止并要求更新凭证；
- 未知协议停止并要求适配器；
- 多账号匹配停止并要求选择；
- 模型部分失败时只展示结果，不允许整源 enabled；运营可删除失败型号后重新验证。

## 11. 首批验收案例

### 11.1 佳杰 / VSTECS：标准协议自动接入

以 `stbl-5` 为一个供应源：输入 endpoint、凭证、明确模型和各自采购比例。系统应创建不可调度
候选执行账号，识别标准 transport，逐模型探测，并按实际采购档位生成一个或多个完整映射；确认后
才进入生产组。`zq-gd` 是另一个合同通道，建立另一个供应源。

### 11.2 FMGo：协议边界

输入 Seedance 2.0 480p/720p 供应源。若标准视频探测通过，则走自动接入；若识别为私有异步
任务协议，候选账号保持不可调度，页面明确显示需要供应商适配器，无任何猜测式上线。

### 11.3 已有百度账号：绑定而非重复创建

以规范化 endpoint 和非敏感凭证指纹唯一匹配账号 90，系统应生成绑定预览而不是新建账号；
验证不得临时把当前不可调度账号加入业务流量。

## 12. 验收标准

- 运营完成新渠道接入无需理解或填写 TokenKey 技术字段。
- 无匹配账号时可幂等创建不可调度候选账号并自动绑定。
- 标准协议、模型清单和逐模型能力均使用真实请求验证。
- 未知协议明确停止，绝不进入生产池。
- 只有期望且探测通过的明确模型进入完整 `model_mapping`。
- 同模型严格按“原生 OAuth → 低 ratio 到高 ratio → 无 ratio 兜底”排序。
- 派生 priority 遵守 TokenKey 数值越小越优先；原生 OAuth 是第一业务层。
- 同一供应源的模型比例不同时自动拆分执行账号，不要求运营拆供应源。
- 采购比例不读写倍率、定价、计费或用户接口。
- 启用失败时不存在部分上线账号。
- 受管账号不能从账号编辑页产生与供应源相冲突的模型映射或 priority。
- 所有变更可审计，所有敏感凭证不进入日志与普通业务字段。

## 13. 实现范围控制

第一版只实现：单供应源编辑、逐模型采购比例、已有账号唯一匹配、标准 API Key 候选账号创建、
标准协议/模型探测、按档位拆分执行账号、完整 mapping、账号级优先级派生、确认激活和审计。

第一版不实现：合同附件、审批流编排、利润分析、采购账单、供应商门户、任意私有协议低代码配置、
模型级 priority、通用后台账号密码自动登录、自动修改 TokenKey 售价或倍率。
