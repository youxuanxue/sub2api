# TokenKey 生产数据库物理增量备份

## 决策与目标

建议使用 pgBackRest 的物理全量、块增量与连续 WAL 归档，替代每两小时 SQL 全量作为主数据库恢复路径。先设计并验证新路径；旧 SQL 恢复的继续调优不作为前置任务。现有 pgdump 和 EBS 快照在过渡期继续提供保护。

依据 2026-10-18 盘点，数据库约 19.30 GiB，单份压缩 SQL 约 2.14 GB、生成约 5 分钟。此前恢复超过一小时未完成，但旧演练容器限制为 0.5 CPU、1 GiB 内存，不能据此推定正常恢复机的耗时。物理恢复保留索引，避免逐行 SQL 导入后重建全部索引；最终速度必须实测。

本文件记录已批准设计，生产启用仍须独立变更确认。现网身份、配置恢复与整机恢复 owner 继续见 [基础设施入口](../../deploy/hetzner/README.md)。不新增业务表或 API，不改变 usage 在线保留期、dedup 去重语义、QA 上传与 DROP 暂停状态；这些不是本次备份方式变更的必要条件。

用户已明确批准按本设计继续实施，增量间隔为每两小时。批准覆盖实现、隔离验证和 PR 准备；不自动执行生产重启、新资源启用或主线合并。

## 2026-10-20 用户决策补充

用户在真实最新及历史恢复验收后明确要求「先把 pgdump 任务停了，数据还继续保留一段时间」，
并接受至少 30 天留存；随后要求对齐 origin/main 整理旧脚本和工作流退役。
这更新下文原计划中的「先观察 48 小时，再降为每日」步骤：允许现在停 prod 旧调度，
取消旧桶自动过期、保留本地与 S3 副本及恢复材料至少 30 天。没有授权删除历史数据、
停 cn-prod 备份、切流、重启生产服务或创建腾讯云付费资源。
真实恢复/遗留验证边界以 [执行记录](../../ops/stage0/physical-backup.md#当前验证边界2026-10-20) 为准；
不能把此决策补充描述成已完成原定 48 小时/七天观测。

用户随后要求「精炼、精准、高效，不要复杂化」，后续恢复改为按需执行，下次结合腾讯云迁机演练。
下文原计划的每周自动隔离恢复暂不推进：移除周定时入口，撤回自动建机和 IAM 扩权草稿；
保留日常备份/WAL/磁盘检查，不改变真实恢复的验收标准。用户随后同意区分备份故障和验证过期：
仅曾成功且超过八天的恢复/仓库验证记录降为每日提醒；缺失、失败和当前备份链故障继续告警。

## 建议配置

| 项目 | 初始设计 |
|---|---|
| 工具 | pgBackRest；选择支持 PostgreSQL 18、当前架构和块增量的版本，验证后固定二进制/镜像摘要 |
| 主数据范围 | 整个 PostgreSQL cluster，包括 usage、余额/配额、dedup 热表与归档表、索引及运维/QA 元数据 |
| 全量 | 每周一次，低峰执行；与同一时段增量互斥 |
| 增量 | 每 2 小时一次，主要保存变化的数据块；同一仓库内由工具管理依赖链 |
| 连续变化 | WAL 持续上传；初始 archive_timeout=300s，归档成功以远端确实持久化为准 |
| 数据损失目标 | 健康状态下最近可恢复点距当前不超过 15 分钟（RPO）；超过即告警，不以任务退出码替代 |
| 恢复目标 | 当前数据规模下，从已就绪隔离机开始拉取备份，到数据库可用并通过关键校验，目标不超过 30 分钟；尚未验证 |
| 可恢复历史 | 稳态至少最近 7 天的连续时间点；启动期如实报告覆盖起点 |
| 清理 | repo1-retention-full-type=time、repo1-retention-full=7；WAL 随所需全量链保留，不另设激进归档期限，由 expire 管理 |
| 存储 | 新建专用私有 S3 仓库，建议沿用现有异地区域；不得放入当前全桶 7 天自动过期的 pgdump 桶 |
| 压缩与粒度 | repo1-bundle=y、repo1-block=y、zstd；从首份全量启用块映射 |
| 并发 | 生产备份从低并发 2 开始，按线上影响调整；独立恢复机可使用 4 并发 |
| 辅助备份 | 新主链路验收后，原 pgdump 降到每天一次，远端保留 7 天、本地保留 2 份；每日 EBS 快照继续覆盖整机文件 |

七天可恢复窗口不等于所有对象七天删除。为了保留窗口边界所依赖的全量，仓库可能保留更老的基础备份；容量预算必须包含该依赖及生成新全量时的暂时重叠。新 S3 桶不配置数据对象年龄删除，仅清理未完成 multipart；有效备份和 WAL 的删除由 pgBackRest 统一拥有。

块增量减少上传/存储重复，不承诺不扫描源文件。物理备份会包含原 pgdump 排除的 ops/QA 表，WAL 也记录这些写入，故不能事先承诺更小的总容量或固定省钱比例。QA blobs、Redis 和主机配置不属于 PostgreSQL 物理备份覆盖，继续由各自备份路径负责。

增量频率决定恢复时需要补放多少变化；连续 WAL 决定最近数据能保护到何时。因此每两小时增量与 15 分钟数据损失目标不冲突。增量采用 UTC 偶数小时的错峰时刻，过渡期避开现有 pgdump；周全量替代对应时段增量。任务串行，同一时刻不执行两份数据库备份，不积累无限补跑队列。未完成、冲突或失败必须形成可见状态，不能把跳过写成成功；连续错过一个正常备份间隔即触发时效检查。

## 乔布斯视角复审

结论：方向成立，交付重点是“故障后能可靠地恢复用户账目”，而非安装一种备份软件。按以下五点收敛：

| 标准 | 对方案的要求 |
|---|---|
| 聚焦 | 本次只交付数据库备份与恢复闭环；表瘦身、明细冷热分层、QA 归档修复和旧 SQL 恢复优化不混入 |
| 简洁 | 一个 pgBackRest 仓库管理全量、增量、WAL 和依赖清理；不自研按 ID 导出、合并或清理器，不新建监控系统 |
| 端到端 | 统一运维入口承担状态查询、备份、隔离恢复和验证；恢复副本有数据、账务校验通过、资源清理完成才产生成功回执 |
| 设计即工作方式 | 运维选择“最新”或“指定时间”，工具解析正确备份链；状态集中呈现最近连续恢复点、实际覆盖起点、最近恢复实测与异常原因 |
| 精品意识 | 30 分钟只是当前规模的数据库恢复目标，必须有独立机实测；真实链断裂、损坏与上传失败不能伪报健康 |

每日逻辑备份负责便携/表级恢复，每日卷快照负责主机及外部文件，新物理备份负责数据库快速恢复，三个角色明确。实现沿用现有调度与观测入口；数据库状态回执不包装成整站灾难恢复成功。应用切回前仍须按既有整机恢复流程核对 Redis、密钥、外部文件与后台任务，防止不同恢复时点的状态混用。

## 部署与恢复边界

1. 为当前 PostgreSQL 基础镜像制作包含固定 pgBackRest 版本的可重建镜像，保持 PG 主版本、架构、运行库、PGDATA 和 UID/GID 兼容。archive_command 在 PostgreSQL 容器内可执行；不把 Docker socket 暴露给数据库。定时备份由宿主现有 systemd/SSM 管理方式编排，配置、权限和观测复用现有 owner。
2. S3 使用实例临时身份或受控临时凭据，限定仓库访问权限；验证容器内凭据获取与轮换，不为便利扩大网关容器的权限。备份传输加密、桶私有并加密存储；恢复机使用仓库只读身份。
3. 当前 archive_mode=off。启用它需要重启 PostgreSQL，因此上线需要一次数据库维护窗口；单实例期间可能短暂影响请求，不能称为零中断或随普通网关蓝绿发布隐式执行。
4. 生产保留同步提交与刷盘保障。初版使用同步 archive-push，不设置会丢弃未归档 WAL 并报告成功的 queue-max 行为。上传失败必须保留待归档 WAL、告警；同时监控 pg_wal 增长和预计磁盘耗尽时间，故障演练证明发现与处置有效。禁止以删除 WAL 来“修好”归档健康。
5. 恢复只写新盘、新 PGDATA；使用兼容版本镜像，不覆盖或挂载生产卷。恢复机只允许读取备份与取得必要镜像/配置，禁止启动计费、供应商访问、退款或 QA 上传/DROP 的后台任务。验证写操作仅作用于恢复副本。
6. 失败回退恢复原数据库启动配置、镜像和定时任务，保留备份仓库及数据。停用连续归档意味着保护能力退回旧路径，须报告实际恢复点，不静默宣称仍达到 15 分钟目标。

## 验收与切换

顺序为：设计 → 小规模可运行原型 → 生产备份链并行运行 → 独立恢复验收 → 降低旧 pgdump 频率。生产资源、重启与正式切换在对应审批后执行；不把旧 SQL 全量恢复跑通作为新路径原型的依赖。

原型验证使用合成数据和真实 PostgreSQL/S3 兼容存储，证明：全量后发生的新增、更新、删除、计费幂等记录可经增量与 WAL 正确恢复；指定时间点恢复排除该时点之后的事务；缺失/损坏 WAL、上传失败及错误目标必须失败。清理边界使用隔离测试仓库验证，不通过删除生产恢复点做实验。

生产验收在独立、与生产同架构的临时恢复机执行，初始按 4 vCPU、8 GiB 内存、足够独立磁盘配置，不复用原来保护线上所用的 0.5 核容器限制。计时分别记录取回数据、还原文件、WAL 重放、数据库启动和关键校验；云主机创建、完整审计及域名切流耗时另报，不能偷换为整站灾难恢复耗时。

必须产出以下证据：

- 从真实远端全量＋增量＋WAL 恢复到最新可达点，以及选定历史点；不能只恢复首份全量。首次验收覆盖一次自然全量到增量的链路；以后每周执行真实恢复，并轮换覆盖保留窗口较老位置。
- 核对完整业务表、usage 分区、主键/唯一约束和序列；逐分区记录行数、时间范围和精确费用汇总；在副本测试同一个计费/退款请求重试不会重复改变余额。费用一致性按真实计费口径验证，不能把 usage 全表费用直接等同于余额差。
- 原型以已知事务及金额作为期望值。生产首次验收创建并记录一个命名恢复点，确认相应 WAL 已上传；先从指定全量＋WAL 恢复到该点，再从较新增量＋WAL 恢复到同一点，两次均使用早于该目标的备份。对恢复结果比较 usage 各分区的记录数、时间、精确费用及稳定行摘要，比较用户余额/配额、计费去重热表与归档表、序列与关键约束。这证明增量链与完整物理路径一致；两者仍共享基础备份/WAL，不声称它替代业务正确性测试。恢复点之后的事务不得出现在结果中；已知重复计费/退款行为在隔离副本另验。禁止将过去恢复库与持续变化的 live 当前值强行比较。
- 连续观测至少两个完整业务日的归档延迟、备份耗时、增量/WAL 字节、CPU/磁盘和业务错误率/延迟；明确全量成本，以及以完整周为周期的容量估算。不能把高写入全库 WAL 当成只有 usage 新增数据。
- 归档延迟超过 15 分钟、备份过期、恢复验收失败、连续恢复链缺口和 WAL 磁盘压力均能触发现有监控告警；恢复点必须来自远端连续可用链，不能仅用最新对象时间。
- 关键恢复检查通过且目标时间达标，才降低旧 pgdump 频率。切换时明确新链实际覆盖起点；旧副本在自身保留窗口内继续保留，新仓库覆盖七天后才宣称具备七天连续恢复能力。

方案达成的首要收益是可验证的较短恢复时间与较小数据损失窗口，其次是减少重复导出/上传。若恢复目标或线上负载不达标，继续调整新链的增量间隔、压缩、资源及恢复配置，不能靠删除对账/去重数据达到指标。

## 执行计划与完成条件

研发先在隔离工作分支交付一个主题明确的 PR，避免混入现有 release followups。原型与部署实现按下表依赖推进；需要确认的生产动作集中成可执行的变更单，不逐步重复询问已经确认的设计方向。

| 阶段 | 工作与交付 | 完成条件 |
|---|---|---|
| 1. 原型验证 | 固定兼容镜像与工具；合成账务数据执行全量、两轮增量、WAL 时间点恢复及损坏/失败测试；验证容器权限与真实对象存储协议 | 新增/更新/删除、分区、序列、重复计费保护全部符合已知期望；失败如实退出 |
| 2. 生产准备 | 形成 S3/IAM、数据库镜像与配置、两小时 timer、统一运维入口、监控及恢复自动化；完成 PR 门禁；生成资源清单、费用上限、维护窗口、预计中断与回退命令 | 代码和原型通过；变更单包含所有实际生产差异，恢复临时机具备自动到期回收与清理验证；生产执行前确认该变更单 |
| 3. 启用并行保护 | 应用已确认变更单；重启启用归档，检查健康和远端 WAL，完成首份全量；运行自然两小时增量；旧备份保持运行 | 首份全量及其必要 WAL 完整，至少一轮自然增量完成；无业务故障；失败按变更单回退，不覆盖业务数据 |
| 4. 独立恢复验收 | 独立机从真实 S3 数据恢复最新点与历史点；完成同点双路径审计和幂等测试；连续观测至少两个完整业务日 | 数据校验通过，单次恢复与关键检查达到 30 分钟目标；连续恢复点落后不超过 15 分钟；完成备份/WAL 用量和线上性能报告 |
| 5. 正式切换与持续验证 | 按变更单中的验收条件将 pgdump 降为每日；新物理链作为主恢复入口；更新运行手册和现有诊断；每周自动隔离恢复 | timer、告警、回执和真实恢复一致；实际覆盖满七天后验证窗口边界仍可恢复；旧副本按自身留存正常退出 |

双路径完整审计属于初次验收额外工作，记录两次各自恢复耗时及审计总耗时，不将两次恢复合计伪装成一次性能指标。每周恢复轮换全量/较新增量及较老时间点，不每次重复双路径全库审计；连续恢复链与远端归档时效日常自动检测。

生产性能比较使用相近请求量/模型结构的基线；先建立门限再启用，网关错误、数据库连接失败、明显 CPU/I/O 饱和或延迟回归触发停用新备份调度并排障，不能为了达到两小时频率挤占在线服务。归档故障仍按 WAL 堆积预案处置，停止定时备份不等于停止 WAL 增长。

若原型或生产验收不达标，保留现有保护路径，在对应阶段修复；不提前降低旧备份频率。完整七天窗口只能随时间建立，不能用首日恢复成功代替；新增/停用云资源和数据库重启不由文档批准状态自动执行。
