# 未知 TTL 缓存创建量结算

## 授权与范围

用户明确选择“未知 TTL 按 1h 收费”，据此解决 Wei-Shaw/sub2api #8412。
这项决定补充 [网关 issue 修复基线](gateway-issue-remediation.md) 中此前尚未裁决的 TTL 差额。
授权实现、测试、提交和推送；不包含部署、旧账追补或支付配置变更。

## 结算契约

- 仅在已有价格 owner 支持 5m/1h 分类时：已知 5m、1h 各按其已解析价格结算，未知量 `max(总量 - 已知明细合计, 0)` 按已解析 1h 价格结算。
- 有总量但完全没有明细也属于未知 TTL，整笔按 1h；不再走旧的全量 5m 回退。
- 已有账号 TTL 强制覆写，以及全局 1h 请求注入对应的既有 5m 计费政策，仍先于结算兜底生效；本次只处理这些政策执行后仍未知的量，不改变其优先级。自定义账号成本统计保留独立规则，不影响本次客户实扣。
- 不按已知明细比例猜测未知 TTL，不修改上游原始总量、5m/1h 字段或响应 usage。价格选择是商业兜底，不能作为上游确实使用一小时缓存的证据。
- 保留已有明细超过正总量时按比例限额的安全归一化；不得重复收费。显式零由现有 SSE presence 规则清除旧明细，最终零写入收费为零。仅缺失总量而有明细的既有兼容行为不变。
- 复用现有定价 owner：渠道单个 cache-write 覆写已覆盖两档，区间与明确 1h 覆写照常生效；明确零价仍为零价。不为缺价发明倍率。无 TTL 分类的模型继续标准 cache-write 价。
- 长上下文、渠道、服务档和用户倍率沿已有结算链生效。只影响新结算，不重算或回写历史账单。

## 实现与验证

结算 owner 为 `BillingService.computeCacheCreationCost`；原始 usage parser 和 `normalizeCacheCreationBreakdown` 不承担未知 TTL 定价，也不伪造明细。

`billing_cache_unknown_ttl_tk_test.go` 覆盖部分 5m、部分 1h、混合明细、全无明细、无差额、超额明细、零写入、原始量不变、定价覆写及长上下文倍率；两个 Anthropic SSE parser 的累计增长/显式零均穿过实际结算函数验证。

页面和下载沿用现有实际费用，无新增 UI 字段；展示的原始 TTL 明细可能小于总量，这是供应商未报告明细，并非全部已知。Web impact: none。

回退代码可恢复原结算策略，但已经结算的账单保持原值；上线验收和部署另行执行。
