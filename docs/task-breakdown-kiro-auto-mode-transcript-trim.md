## 目标与当前结论

处理 Claude Code auto-mode 安全分类请求在 Kiro 上的尺寸不兼容，同时尽量保留其授权判定所需的上下文。
请求变小或不再报 413，不能单独作为修复成功的标准。

2026-10-26 的直连重测已取得新的容量边界证据，用户明确批准放宽阈值这一方向；
“不重复探测容量边界，也不放宽阈值”这条原立场由本文件《新证据二》取代。
放宽阈值本身不是修复：它真正解决 45 次一次性突发，只推迟 38 次 cron，
另有 6 次为保留安全余量刻意不救、30 次任何阈值都救不了。
网关承担兼容责任，但采用“结构化减肥”而不是按字符猜测内容：保留用户原话和最新动作，
研究能否去掉与当前判定无关的旧工具过程记录；无法安全判断时继续 413。
记录较旧或工具可重新执行，并不证明记录与当前判定无关。
但《新证据一》已验证：这批 413 的 wire 正文里不存在结构化工具记录，该路径在这批流量上无事可做。

本文件是修订后的方案建议，保留 pending 状态，不把会话中的方向确认扩大为生产上线授权。

本地预算的实现 owner 为 [translator.go](../backend/internal/integration/kiro/translator.go) 的

此前上游实测与本次离线前缀实验是不同证据，不混写为同一次完整线上重放。

## 新证据一：auto-mode 流量结构实测（2026-10-26）—— 否决本文件的优先验证路径

**已验证：本文件列为“优先验证”的「网关按结构删除旧工具过程记录」路径，在这批 413 流量上没有可删除的对象。**
证据来自 prod QA blob 结构测量（近 26 小时窗口内三个 UA 的 413 样本）：

| 组成 | 字节 | 占比 |
| --- | --- | --- |
| `system`（含一个 138,752 B 带 `cache_control` 的 wire element） | 139,156 | 约 14% |
| `messages`（2 个 user 轮，**零 assistant 轮**） | 约 840 KB | 约 86% |
| `tools` / `input_schema` | 0（key 不存在） | 0% |
| `tool_result` / `tool_use` / 图片 | 0 次出现 | 0% |

- 零 assistant 轮说明这是首轮请求，不是累积对话；history 里没有任何东西可丢。
- 零 `tool_result` / `tool_use`：`tool_calls_present=false` 在全部 54 行近期 413 QA 记录上成立。
  该 flag 基于**完整** body 计算，不是 256 KiB 前缀截断的产物，因此不受 QA 前缀上限影响。
- transcript 以 **user 角色 text block** 拼装（turn 2 为 69~71 个 block，单块 87 B 到 28,623 B），
  正是本文件对 `jGo` 的静态分析所预测的形状。**wire 格式里不存在结构化工具记录供网关整条删除。**
- 本文件的 system 块字节数一律用 **wire element** 口径（含 JSON 包装）：
  分类器块是 138,752 B，其中 text 字符串值本身 138,692 B，`{"type":"text","text":` 加
  `,"cache_control":{"type":"ephemeral"}}` 的包装与引号共 60 B。
  用 wire element 是因为 `maxPayloadBytes` 作用于序列化 body，138,752 才是计入限制的量；
  138,692 只在讨论 prompt 文本本身时才相关。

所以候选路径第 6 步（从旧到新整条删除旧工具过程记录）在这批流量上收益为零。
这不等于该路径对其它 Kiro 流量无效，但它不再是这批 413 的优先验证对象。

同时验证了 auto-mode 签名，此前这些只能从客户端静态分析推断：

| 签名 | 状态 |
| --- | --- |
| `<transcript>` 标记，每请求 2 次出现 | 已验证存在于 prod 入站正文 |
| `max_tokens: 64` | 已验证（本文件此前只写“小输出预算”） |
| 安全分类块（`system[1]`）138,752 B wire element，带 `cache_control` | 已验证，逐块哈希比对（本轮唯一强度**上调**的结论） |
| `querySource` / `auto_mode` 字面量 | 0 次出现，与本文件既有声明一致 |

### `workload/cron` 不是独立负载

三个 UA（`workload/cron`、`claude-cli/2.1.301 (external, cli)`、`claude-cli/2.1.302 (external, cli)`）
的**分类器块 `system[1]`（138,752 B）和尾部块 `system[2]`（287 B）逐字节相同**，
已由逐块哈希验证（`system[1]` text `168a6de892af` / element `ab34e2627b1a`，`system[2]` `bb7148e5a3a6`，
三个 UA 全部一致）。`max_tokens` 均为 64，turn 2 均为 69~71 个 block，
assistant 轮 / tools / 图片全部为 0。cron 只差调度方式，请求形状一致。
本文件对 `2.1.301` 的分析可以无修改地适用于 cron 行；把 cron 当成独立负载是错的。

**范围限定：相同的是这两个块，不是整个 `system` 数组。** `system[0]` 是一个小的 per-client 前导，
每个 UA 的 `text_sha12` 都不同（cron `ae8c2fd79099`、2.1.301 `f11cdfdf1aef`、2.1.302 `c10cfd7d16ee`），
cron 为 113 B element / 90 B text，另两个 UA 为 95 B / 72 B。
因此 `system` 数组总长在三个 UA 上分别是 139,156 / 139,152 / 139,134 B：
差额 = 4 B 数组标点 + 18 B 仅在 `system[0]` 的真实内容差异。
不要把本节读成“system 块跨 UA 相同”。

### 增长是锯齿状的，不是无界的

成功的非流式 cron 行显示重复周期：10-24 19Z p50 = 284,080 → 10-24 20Z 重置到 40,853；
10-26 09Z max = 298,756 → 10-26 10Z 重置到 53,090。每周期从约 50-60k tokens 起、
累积到约 250-300k 后重置（符合 session 或工作单元边界），413 只发生在周期上半段。
**且峰值逐周期上升：255,860 → 258,752 → 298,756**，所以今天靠抬阈值买到的余量明天更小。

## 新证据二：Kiro 容量边界直连重测（2026-10-26）

本文件原来的立场是“不重复探测容量边界，也不放宽阈值”，依据是 PR #2688
（commit `df262d901`，2026-10-17）记录在 [kiro-payload-overflow.md](approved/kiro-payload-overflow.md)
的实测：同一账号 + `claude-opus-5.5` 接受 921,600 与 950,000，拒绝 999,999 / 1,000,000 /
1,048,576 / 2,435,861，记为“边界在 950,000~999,999 之间”。

那份已批准文档自己正确声明了既有证据**不能**推断“所有模型、端点和未来版本都具有完全相同的精确字节边界”。
本次重测填的正是它自己标出的这个缺口 —— 不是“文档错了”，而是把它的保守立场收紧到可用的精度。
用户已明确批准放宽阈值这一方向。

方法：直连 `runtime.us-east-1.kiro.dev/generateAssistantResponse`，合成 `x` 填充，
账号 305/325/326，共 39 次上游请求。

### 已验证

1. **阈值与模型无关 —— 此结论待确认，可能反转。** 同一账号（325）上 `claude-sonnet-5` 与
   `claude-opus-5.5` 的阶梯逐字节一致：均接受 921,600 / 985,088 / 993,024 / 996,992 / 997,984，
   均拒绝 998,976 / 1,016,832 / 1,048,576。

   **待确认（2026-10-26 后续探测）：** 同账号（325）、同形状、同字节 920,000 下，
   仅 `modelId` 不同即得到不同结果 —— `claude-sonnet-4.5` 返回 400
   `CONTENT_LENGTH_EXCEEDS_THRESHOLD`，`claude-sonnet-5` 与 `claude-opus-5.5` 均 200。
   据此 `sonnet-4.5` 的阈值在 30 万~35 万之间，而不是 99 万，提示本条可能仅适用于部分模型。

   但该差分建立在**混合基准**上：`sonnet-4.5` 的拒绝在真翻译器输出与手搓 body
   两种基准上均复现，而 `sonnet-5` / `opus-5.5` 的接受**仅在手搓 body 上测得**。
   同一基准的对照补测进行中（用真翻译器输出重测 `sonnet-5` 的 920,000），两种结局：
   补测 200 则模型差分成立、本条须改为“仅适用于部分模型”；补测 400 则该差分是手搓基准的
   假象、本条反而站得住。**在补测确认之前不应依据本条做阈值决策**，
   也不要据此假设任一模型的边界等于本节其它数字。
2. **阈值与账号有关，此前未知。** 326 的边界落在 (993,815, 993,831]（16 字节区间）；
   305 落在 (993,815, 994,100]（285 字节区间，**包含** 326 的区间，与其一致）；
   325 落在 (998,387, 998,400]，高约 4.5 KB。
   准确表述是“至少存在两档边界”：两个账号落在同一 16 字节区间，第三个高约 4.5 KB。
   3 个样本不足以判定哪一档是常态 —— 2 个一致、1 个偏高在统计上无法区分
   “325 偏高”和“326/305 偏低”；若真实分布是双峰，两档都是常态。
   **不要**写成“per-account 离散 4.5 KB”（暗示从未证明的连续变化），
   也**不要**写成“325 是异常值”（这同样是推断，不是观测）。
3. **这不是抖动。** 996,101 在 326 与 305 上各 4/4 拒绝；325 的边界在后续调用中逐字节复现。
4. **原 950,000 不是边界，只是当次探测的最大取值。** PR #2688 未在 950,000~999,999 之间取点。
   现有 921,600 相对已观测最低边界（993,815）的真实余量约 **72,215** 字节，
   而不是已批准文档所述的 28,400 —— 后者是相对 950,000 这个探测取值算出来的。
5. **测量面是整个序列化 body**，不只当前消息：把填充移入 history 轮次得到与 325 完全相同的边界。
6. **线上从未观测到上游容量拒绝。** `ops_error_logs`（保留期自 2026-10-11，417,872 行）中
   `CONTENT_LENGTH_EXCEEDS_THRESHOLD` 计数为 **0**；119 次有字节记录的 413 全部由本地保护拦截。
   这证实了“本批错误没有上游调用”的判断，也说明真实上游边界**只能**靠直连探测获得。
7. **PR #2688 未留下任何探测脚本或账号标识**，无法复现；所以本次重测不是重复劳动。

### 建议阈值与它的定位

建议 **962,560 字节（940 KiB）**，已在 326 与 305 上实测接受。

962,560 的定位必须写死：它是“覆盖已观测最低边界（993,815）并留 31,255 字节余量”的取值，
**不是安全上限**。

它的安全性只依赖已观测最低边界这一个观测量，**不依赖**哪一档边界是常态的判断。
即使 325 那一档后来被证明才是常态，962,560 仍在最低观测边界之下。

### 仍然未知（不得省略）

- 24 个账号中只探测了 3 个，其余 19 个 402 耗尽、2 个 403 失效。
  若某个未探测账号的边界低于 962,560，该账号上仍会 413。
- 两档边界相差约 4.5 KB 的成因无法解释（以 325 与 326 的对照排查）。已排除：凭据字段长度
  （access_token 232 / refresh_token 232 / profile_arn 65，325 与 326 一致）、
  region（全部 `us-east-1`）、创建日期（全部 2026-10-16）、
  plan（全部 `KIRO POWER` / `Q_DEVELOPER_STANDALONE_POWER`）、
  `channel_type` / `tier_id` / `quota_dimension`。
  名称前缀也不解释：325 与 326 同为 `us4-` 却差 4.5 KB，305（`uk1-`）与 326（`us4-`）一致。
  差异在上游侧，我方 DB 不可见。
- 全部测量取自单日，时间稳定性未测。已批准文档关于“未来版本边界可能移动”的警告继续有效。
- **模型维度未定。** 见上文第 1 条：920,000 字节上 `sonnet-4.5` 被拒（推得其阈值约 30 万~35 万）
  而 `sonnet-5` / `opus-5.5` 被接受，提示边界可能随模型变化；但该对照跨了真翻译器输出与
  手搓 body 两种基准。同一基准的补测完成前，**不得假设 962,560 在所有模型上都被接受**，
  也不得依据“与模型无关”做阈值决策。
- **网关路径未验证。** 本次是直连上游探测，未确认 TK 翻译后的 body 与合成 body 同尺寸。
  实测反而显示翻译后 body 显著小于 ingress：同形状请求 ingress 966,247~984,081，
  翻译后 928,064~958,922。**抬高 `maxPayloadBytes` 前必须经 `/v1/messages` 验证。**
- [kiro-lb 的容量实验](https://github.com/minpeter/kiro-lb/pull/26) 仍不作为放宽依据；
  本节结论不引用它。

### 收益归因

按 119 次有字节记录的 413 分类，940 KiB 的收益不能简化成{0}83/119{1}这种单一数字：

| 分类 | 次数 | 940 KiB 的效果 |
| --- | --- | --- |
| 非 cron 一次性突发，≤ 962,560 | 45 | **真正解决**，不会重新累积 |
| cron，≤ 962,560 | 38 | **仅推迟**。940 KiB 对这批请求只多出约 3,638 字节余量；按实测 3,840 B/h 约 1 小时，按当日 15,800 B/h 约 15 分钟 |
| 非 cron，962,560 < 尺寸 ≤ 993,815 | 6 | **刻意不救**。更高的阈值可以救这 6 次，940 KiB 为保留安全余量明确让出了这一档 |
| 任何阈值都救不了，> 993,815 | 30 | 必须靠内容裁剪。包含全部 14 次 `opus-5-5` 与 2 次 `opus-5`，最大 1,885,268 字节 |

四类合计 119，与有字节记录的 413 总数一致。按 cron 维度拆：
非 cron 81 = 45 + 6 + 30，cron 38 = 38 + 0 + 0。

第三类是 940 KiB 这个取值的**可见代价**，不是统计遗漏：960 KiB 可救 87（+4），
抬到已观测最低边界本身可救 89（+6，即救下全部第三类）。
多救 4~6 次的代价是让出大部分安全余量，不推荐。

抬高阈值不等于这批客户的 413 已解决：45 次真正解决，38 次只是推迟，6 + 30 次仍然 413。

## 为什么撤回通用裁剪策略

Claude Code 2.1.301 的分类器提示明确使用 assistant 提案解释用户简短的“同意”，
使用中间第三方消息判断该确认是否存在歧义，并读取工具结果、动作和附属上下文。
因此，assistant 文本和工具输出不能仅凭角色名就全部删除；只保留最新用户意图和最新动作也会丢失更早的范围限制、禁止或撤回。
单条消息只保留头尾可能删除中间的否定句、作用对象或命令参数。
添加“已截断”标记只能告知信息缺失，不能恢复这些信息或保证分类器保守拒绝。

以下是离线候选路径。《新证据一》已验证第 6 步在这批 413 流量上无可删除对象，
因此它不再是优先验证对象；整条路径保留，作为其它 Kiro 流量的候选。本 PR 不实现或启用它：

1. 先测量转换后的真实大小，并保留原始请求诊断。
2. 只在已识别为 Claude Code auto-mode、且 transcript 是逐行结构化记录时进入此路径；普通 user 文本不进入。
3. `<transcript>`、结尾标记和最新 action 完整保留；不在 JSON 记录中间按字节切断。
4. 所有真实 `user` 记录原文保留，包括早期禁止、范围限制、撤回和第三方消息；用户原文是授权证据，不能为了凑大小删除。
5. 最新工具调用及其参数完整保留。最新 action 前紧邻的 meta/outcome 记录一并保留，避免丢失执行状态。
6. 超限时从最旧到最新依次删除**完整的旧工具过程记录**（如已经结束的 Bash/Read/Write/Edit 调用及其结果），每删一条都重新测量；删除记录之间插入固定的“旧工具过程已省略”标记。
   这一步不删除用户话、不改写最新 action，也不把工具内容误当用户授权。
7. 如果仍然超限，再删除最旧的非授权元数据记录；不得删除用户记录、最新 action、授权链或安全系统提示。
8. 仍超限就保持现有 413，不调用上游。不能用 assistant 文本摘要、单条 head/tail 裁剪或模型自动总结来强行塞入。

这条路径用于测量删除旧工具记录的空间收益，尚未证明这些记录可以丢弃。
例如，最新动作执行此前 Write/Edit 写入的文件时，旧记录中的文件内容就是审查当前动作的依据；
只保留用户原话、最新动作和相邻 meta/outcome 不足以保留这类依赖。
候选路径只有在完整样本上验证尺寸收益及判定影响后才能进一步评审。
解析失败时返回 413 只能保护格式边界，不能证明成功解析后的删除保持了原判定。

社区证据的正确用法：

- [iTerm2 AutoModeClassifier](https://github.com/gnachman/iTerm2/blob/ad80b196b4447bd6a99b572de7009dc1ad59db8d/sources/AITerm/AutoModeClassifier.swift)
  对自己的结构化历史做容量限制，待审动作另行传入；其角色类型和安全提示与 Claude Code 不同。
  它证明客户端可以设计有界分类输入，不能证明代理可以直接照搬其裁剪策略。
- [claude-auto-permission](https://github.com/kevinhwang/claude-auto-permission/blob/d015838/docs/llm-classifier-design.md)
  使用自己的输入投影和判定规则；删除 assistant 文本的做法不能脱离那套分类器使用。
- 已检查的 KiroProxy、kiro-lb 实现主要裁剪外层历史；未找到可直接复用、已验证适配该版本 Claude Code 安全 transcript 的裁剪实现。
- [kiro-lb 的容量实验](https://github.com/minpeter/kiro-lb/pull/26)
  使用不同模型和账号，不能推翻本项目此前上游实测，也不能作为直接放宽本地保护的依据。

## 当前交付范围

本 PR 只完成已获授权的诊断改动，不增加 transcript 解析器、原型入口或裁剪开关：

- Kiro 本地超限记录转换器输入大小/hash、现有裁剪前后序列化大小以及 system、history、current text、工具等组成。
  转换器输入可能已经过 schema 等处理，不标为原始入站 wire。
- QA 区分实际读取的 wire 字节/hash、读取是否完整，以及保存/脱敏后正文的字节/hash。
  只有读到 EOF 且无读取错误时才声明完整 wire hash；不改变旧 `request_sha256` 的含义。
- 新增诊断只包含大小、计数、完整性和 hash，不附加用户正文，不扩大 QA 正文保存上限。
- 所有请求沿用现有裁剪与本地 413 路径，包括 auto-mode transcript；不新增任何正文改写。
- 诊断测量现有转换和裁剪前后的 Kiro payload；不因尺寸错误跨账号重试，不放宽 Kiro 限制。
- 本次不输出 transcript 检测结果或删除类别/条数；这些属于尚未实现的候选实验。

本方案不修改生产服务、账号、路由、计费、超时或权限模式，不伪造分类器允许结果。

## 用户可见的处理路径

| 路径 | 价值与代价 | 当前状态 |
| --- | --- | --- |
| 在客户端使用普通权限确认模式 | 避开这类 auto-mode 辅助分类请求；增加用户确认次数 | 待在受控客户端验证；不代表所有大请求都不会超限，不自动代用户切换 |
| 显式选择已验证能承接完整输入的供应源 | 保留自动模式及完整分类输入；供应源、费用和数据去向可能变化 | 当前未选定供应源；不自动跨平台路由 |
| 客户端压缩或修复其分类器输入生成 | 客户端掌握真实角色和协议，更适合决定输入组织方式 | 未验证具体版本、配置或修复；不能承诺升级或 `/compact` 一定有效 |
| 网关按结构删除旧工具过程记录 | 在这批 413 流量上收益为零：wire 正文里零 `tool_use` / `tool_result`（《新证据一》） | 不再是优先验证对象；留作其它 Kiro 流量的候选 |
| 抬高 `maxPayloadBytes` 到 940 KiB | 解决 45 次一次性突发；38 次 cron 仅推迟约 15 分钟~1 小时；6 次刻意让给安全余量、30 次仍 413 | 阈值证据已就绪（《新证据二》）；落地前须经 `/v1/messages` 验证网关路径，并单独评审 |
| 网关按标签删除、摘要或头尾截断 transcript | 有机会缩小正文，但会改变安全审查材料 | 明确不实施 |

诊断交付与用户体验修复分别验收。普通权限确认会减少自动化，不能悄悄作为默认产品修复；
保留自动模式的长期处理仍需客户端兼容修复或能承接完整输入的供应源。

## 验证与完成标准

诊断改动按既有测试验证：小请求转换结果不变；超限仍返回 413 且不调用上游；
现有裁剪前后各项字节组成可核对；内部错误细节经过 middleware 保留且不泄露到公开响应。
QA 覆盖相同前缀不同尾部、恰好达到捕获上限、未完整读取、读取错误和 gzip wire/解码口径。
复用已有 Kiro、QA、service 和 handler 聚焦测试与 preflight；本文修改本身不新增测试代码。

## 原型验收门槛

容量边界调研已由《新证据二》完成，此处不重复；只验证结构识别、删除顺序和安全保留项：

1. 明确支持的实际格式、版本、角色来源、转义及边界规则；伪造标签、嵌套标记或无法判断的输入不得改写。
   UA、`<transcript>`、小输出预算等特征只能用于识别候选，不能独立授权删除正文。
2. 对逐行 JSON 记录做完整解析；任何解析错误、重复结束标记、缺少最新 action 或记录角色不明，都直接保持原文并 413。
3. 测试用户原文完整保留，最新 action 和相邻 meta/outcome 完整保留，旧工具记录只按从旧到新的顺序整条删除。
4. 用完整受控样本覆盖允许与拒绝、先禁止后简短确认、撤回、assistant 提案后的确认、第三方插入、
   中间否定和伪造角色、执行或提交此前 Write/Edit 写入的文件等场景；
   先验证未修改输入的预期判定，再对比减肥后的判定。
5. 分别报告尺寸达标、上游接受和安全判定结果。通过有限样本不宣称普遍语义等价；
   缺少完整原请求时，不宣称已逐条修复这批事件。

当前候选是“旧工具过程记录整条删除”；assistant 摘要、用户消息删除、单条 head/tail 裁剪和模型总结均淘汰。
满足以上门槛前不进入生产；诊断通过也不代表网关减肥器可以上线。
