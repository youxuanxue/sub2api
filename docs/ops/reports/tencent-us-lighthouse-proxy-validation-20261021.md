## 管理与代理边界

两台 Ubuntu 24.04 x86_64 的 TAT Agent 1.2.2 在线，实际 root 命令成功。无需 SSH 密钥；公网拒绝入站模板在创建时绑定。之后关闭两台 SSH service/socket，管理保留 TAT。

代理使用 GOST v3.3.0，下载物核对 GitHub 发布的 SHA256。以专用无登录用户和 systemd 沙箱运行；只监听私网地址，云防火墙和宿主防火墙仅允许验证主机私网源访问 TCP 1080。服务启动依赖来源限制规则，规则随重启恢复。

## 停写、最终 WAL 追平与切流时间估算

**当前不能承诺秒级切流。预先建好并持续追平 standby、完成应用预热和写隔离演练后，暂按核心写入不可用 3–8 分钟估算，维护窗口预留 15–30 分钟。此处为规划值，尚非切换演练实测。** 本轮未执行任何停写或切流动作。

只读依据：11:07:57.874 至 11:10:10.880 UTC 的 133.006 秒里，源 LSN 从 `1A/BCE6EFF0` 增至 `1A/BF68D358`，相差 42,066,792 字节，约 **18.10 MiB/min**。这是短窗口速率而非峰值容量保证。两次快照 archive failed_count 均为 0，当前 WAL 与 last_archived_wal 相邻；末次归档距快照约 12 秒。源 archive_timeout 为 5 分钟、segment 16 MiB；按本窗口速率，5 分钟约生成 90.5 MiB WAL。没有目标持久 standby 的 replay LSN，因此这些数据不能当作实测目标追赶耗时。

| 阶段 | 暂估 | 必要前提 |
|---|---:|---|
| 预先恢复、验证并持续追 WAL | 提前完成，不放进停写窗口 | 当前隔离恢复工作区不能直接充当持久生产 standby |
| 停止接收新请求/后台写入，排空在途并验证源写隔离 | 1–3 分钟 | 有明确长流截止与重试策略；无限等待长流则无固定上限 |
| 最终 WAL 完整归档、目标重放到最终 LSN | 30–120 秒 | standby 已近实时追平，归档和下载通畅；只在获批窗口触发最终归档 |
| 目标晋升、应用启动/预热与关键验收、入口切换 | 1–3 分钟 | 配置、证书、镜像、发布路径事先验收 |
| DNS 缓存收敛 | 通常再考虑约 5 分钟，可能更久 | 当前公网 A 记录 TTL 300 秒；旧缓存、长连接不受一次修改立即控制 |

前三个窗口内步骤合计约 2.5–8 分钟，按 **3–8 分钟**规划。DNS 收敛可能使部分用户的实际不可用时间更长，不能与“目标已可写”混为一谈。提前降低 TTL 可以缩短常规 DNS 缓存，但必须先经过原 TTL，且需单独授权修改；本轮没有改 TTL。旧入口仍收到请求时应保持写隔离，维护响应或经事先验证的转发方案处理，禁止双主写入。

若最终归档只等待自然 archive_timeout，则可能额外等约 5 分钟（繁忙时 segment 满会更早），不能套用上述 30–120 秒假设。compose 的 180 秒停止宽限也不是所有长流必定在 3 分钟内完成的保证。只读快照中的短数据库事务同样不能代替 HTTP 长流排空证据。

若不预建 standby、停写后才从 S3 冷恢复，本轮既有完整恢复路径耗时约 20–31 分钟（含仓库检查、审计及验收；历史点与最新点不可混同），还要应用启动和切换核验，应暂按 **30–60 分钟**窗口准备，不建议采用该方案。完整恢复用时不能直接当作最终少量 WAL 追平时间。

缩小估算范围仍需：持久 archive-recovery standby 与最终 LSN 闸门、可恢复/可告警的持续追赶计时、所有写者隔离与长流 drain 演练、目标应用与账务冒烟、新 timeline 备份保护、旧入口请求处理和失败回退边界。目标一旦开始业务写入，不能简单解冻旧库回退。正式窗口及所有生产变更仍需另行批准。
