内存规划参考量为 `MemTotal - MemAvailable + SwapUsed - SwapCached`，包含后台和冷匿名页，不等于进程 RSS。容量关系用 `后台基线 + 峰值在途数 × 每请求内存包络 + 安全余量` 规划；由于没有历史进程 RSS/Go heap，本次不声称得到精确单请求内存系数，也不能由此证明内存泄漏。SAR CPU 是采样区间平均，内存是采样点，须按真实时间对齐。

us6 在 36 个生图在途的采样点，该规划参考量为 3.783 GiB；8 GiB 约为其 2.1 倍。此倍数只表示对已观测需求增加缓冲，OOM 截断意味着它不是需求上界。prod 在 105 个生图在途时该量约 4.706 GiB，仍有约 3 GiB 可用内存，支持本次暂不扩容 prod。

2 GiB 已出现几乎耗尽内存和 swap 的证据。8 GiB 是本次批准的内存过渡方案；CPU 核数不增加，仍需观察高峰 CPU 和延迟。历史总生图在途 111，在四台均分下约 28/台；单台维护时均分约 37/台，实际还受账号能力、粘性、非生图流量与分配不均影响，不能作为安全并发上限。原先面向高峰和 N-1 的规划是 4 vCPU / 16 GiB，但本次不执行该规格或 prod 扩容。

## 数据与用户体验保护

逐台迁移。记录全部平台镜像原 schedulable 状态，暂停目标节点新请求；SIGUSR1 排空，HTTP 在途和 Redis 异步 processing 任务连续三次归零才停写。停应用和定时任务后生成新 pg_dump，验证 S3 往返 SHA-256，并在隔离 PostgreSQL 中实际恢复和比对核心表数量。

普通 pg_dump 排除了 usage/ops/QA 日志数据，因此完整冷磁盘快照才是全量迁移载体。Redis 显式 SAVE，正常停止数据库和全部容器，关闭 Docker 自启动，生成 PostgreSQL、Redis、app、Caddy 和密钥配置文件的 SHA-256 清单，然后停止原机、创建完整快照。

新机从冷快照创建，业务保持停止，重新注册独立 SSM 身份。先比对全部冷文件、核验 8 GiB 内存，再保留原 Static IP 和防火墙策略启动原镜像，比对数据库核心表数量和镜像 ID。健康和真实业务验证通过后恢复原调度状态，再迁移下一台。

旧机保留停止状态。新机一旦启动应用，就可能产生计费、OAuth 刷新或其他写入，禁止直接回切旧磁盘；此时回退必须先排空新机并迁回最新状态。不能承诺绝对零延迟波动；单节点离线期间其他节点负载会增加。

### 40 并发保护的准确含义

40 张全部成功，但不标成安全容量通过。UTC 11:37:28，连续三次采样存在换页活动（8、20、7 页），触发既定的“连续三次换页或 PSI”保护，执行器停止后续加压并等待全部请求自然完成。本轮没有为了过关降低阈值或追加请求。

40 档最低可用内存 3324 MiB（3.25 GiB），高于 1.5 GiB 停止线；应用 RSS 峰值约 3.66 GiB，swap 占用最高仅 0.5 MiB（30 档时已有 0.25 MiB），并非 swap 接近用满。全部采样 memory PSI avg10 为 0.00；收尾主机累计 some/full stall 约 66.6/62.0 毫秒，存在极短暂事件，不能写成完全没有任何 stall。没有 OOM、容器重启或测试请求的 TLS/HTTP2 错误。保护规则偏保守，这个结果既不能证明机器已扛不住，也不能证明持续 40 并发安全。

各波主机非 idle、非 iowait CPU 采样均值约 14% / 22% / 24% / 36%，20/30/40 档都出现短时 100%。该 CPU 指标含 steal；另查 SAR 的 11:10–11:20 窗口 steal 仅 0.03%，当次实时样本为 0。平均值包括尾部少量在途阶段，不能据此认定满并发时还有同等 CPU 余量。Lightsail 的 CPU burst 长时间可持续性本轮未验收。

### 用请求与内存关系估算规格

排空后的基线 `MemTotal - MemAvailable` 约 960 MiB。20/30/40 波次的主机峰值使用量，扣除该基线，再除以本档并发，约为 86 / 94 / 88 MiB/请求。这里是整个批次响应集中返回时的峰值摊销，包含 Go 堆、缓冲、内核和其他容器影响，并非每个请求恒定占用；内存峰值发生时部分请求已完成，不能按那一瞬间剩余在途数线性外推。

对本次单参考图、单张 2K 输出，可先用 `约 1 GiB 基线 + 0.1 GiB × 生图并发 + 至少 1.5 GiB 余量` 做规划：30 并发约需 5.5 GiB，40 并发约需 6.5 GiB。当前机器实际可见总内存约 7.64 GiB，因此 2 核 / 8 GiB 作为过渡配置有实测依据；2 GiB 明显不足，4 GiB 也不足以为 30–40 并发保留可靠余量。

建议暂按常态 20–30 并发规划单台 Edge，再做持续负载验收；40 只能作为本轮观察到的短时突发，不把账号配置 `4×25=100` 当成主机可承载的生图并发。多参考图、大文件、4K、多张输出和长时间运行需要另测。用 Little 定律估算到达率必须使用稳定窗口的平均时延：例如平均约 50 秒时，30 个持续在途约对应 36 次/分钟；本轮波次不是稳态，该数只是规划换算。持续 40+ 并发若出现 CPU 或额度压力，再评估更多 Edge 分担或 4 核 / 16 GiB，不能单靠继续加内存。
